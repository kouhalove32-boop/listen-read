# 開発の進め方

## スプリント（1 週間）
| いつ | 何をする | 成果物 |
|---|---|---|
| 週のはじめ | **計画**：ゴールを 1 文で決め、Issue を選ぶ | マイルストーン「Sprint N」と、そのゴール |
| 週の途中 | **開発**：1 Issue ＝ 1 ブランチ ＝ 1 PR | PR（CI が通ること） |
| 週の終わり | **レビュー**：実機（iPhone と Windows）で動かして確認 | リリース（Pages と exe） |
| 週の終わり | **ふりかえり**：よかったこと、困ったこと、次に試すこと | `docs/sprints/sprint-N.md` |

プロダクトオーナー（何を作るか決める人）は本人。Claude は設計・実装・テストを担当し、判断材料を出す。

## Issue のルール

### 着手できる条件（Definition of Ready）
- ユーザーストーリー（誰が・何を・なぜ）がある
- 受け入れ条件がチェックリストで書かれている
- 大きさが **S（〜半日）/ M（〜2日）/ L（それ以上 → 分割する）** で見積もられている

### 完了の条件（Definition of Done）
- [ ] 受け入れ条件をすべて満たす
- [ ] CI（テスト）が通る。ロジックを変えたらテストを足す
- [ ] iPhone（PWA）と Windows（exe）の両方で動作を確認した（関係する場合）
- [ ] 設計を変える判断をしたら ADR を書いた
- [ ] 利用者に見える変更なら README かヘルプを更新した

## ラベル
| 種類 | ラベル |
|---|---|
| 種別 | `type:story` `type:bug` `type:tech-debt` `type:spike`（調査） `type:docs` |
| 優先度 | `P1`（今すぐ） `P2`（次のスプリント） `P3`（いつか） |
| 大きさ | `size:S` `size:M` `size:L` |
| 領域 | `area:web` `area:desktop` `area:audio` `area:content` `area:ci` |

## ブランチと版
- `main` は常に公開してよい状態に保つ。作業は `feat/…` `fix/…` `chore/…` のブランチで行い、PR でマージする
- Web 版は main へのマージで即反映される。Windows 版は `desktop-v1.0.<run>` として自動でリリースされる
